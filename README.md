# MAN_inspection — Activity Logger

โปรแกรมบันทึกกิจกรรมการใช้งานคอมพิวเตอร์ (Windows) ของเครื่องตัวเอง แล้วเก็บลงไฟล์ Excel
พร้อม build เป็น `.exe` และอัปเดตตัวเองอัตโนมัติจาก GitHub Releases

> โปรแกรมนี้โปร่งใส: มีไอคอนอยู่ที่ system tray ให้เห็นว่ากำลังทำงาน เปิดโฟลเดอร์ log หรือสั่งปิดได้

## สถาปัตยกรรมโดยรวม

มี **2 repo** แยกหน้าที่กันชัดเจน:

| repo | การมองเห็น | หน้าที่ |
|------|-----------|--------|
| `T-TFIG/MAN_inspection` (repo นี้) | **Public** | โค้ด + แจก `.exe` ผ่าน GitHub Releases เท่านั้น ไม่มีข้อมูลพนักงานอยู่ในนี้เลย |
| `T-TFIG/MAN_inspection-data` | **Private** | ที่เก็บกลาง: policy, สถานะ/heartbeat ของแต่ละเครื่อง, ไฟล์ Excel ที่อัปโหลด |

มี **2 โปรแกรม** ใน Release:

| ไฟล์ | ใครใช้ | ทำอะไร |
|------|--------|--------|
| `MAN_inspection.exe` | พนักงานทุกเครื่อง | บันทึก log + ส่ง heartbeat/อัปโหลด log ไป data repo ตาม policy (ไม่ต้องตั้งค่าเอง) |
| `MAN_inspection_admin.exe` | admin เท่านั้น | Dashboard เห็นสถานะทุกเครื่อง + แก้ policy ทั้งหมดจากที่เดียว |

## บันทึกอะไรบ้าง

| Event | ความหมาย |
|-------|----------|
| `Window` | โปรแกรม/หน้าต่างที่ใช้ พร้อมระยะเวลา (วินาที) ที่อยู่หน้าต่างนั้น |
| `Idle` | ช่วงที่ไม่ได้แตะเมาส์/คีย์บอร์ดเกิน 60 วินาที (ปรับได้) |
| `Active` | กลับมาใช้งานหลัง idle |
| `Lock` / `Unlock` | ล็อก / ปลดล็อกหน้าจอ |
| `Logon` / `Logoff` | เข้า / ออกจาก session |
| `USB` | เสียบ / ถอด USB หรือไดรฟ์ที่ถอดได้ (พร้อม drive letter) |
| `Start` / `Stop` | โปรแกรมเริ่ม / หยุดทำงาน |

> หมายเหตุ: บันทึกแค่ "ชื่อโปรแกรม + ชื่อหน้าต่าง + เวลา" เท่านั้น ไม่ได้เก็บการพิมพ์ (keystroke) หรือภาพหน้าจอ
>
> แยกจากนี้ยังมี **heartbeat** ส่งไปที่ data repo ทุก ๆ 5 นาที (ปรับได้) มีแค่ hostname + เวอร์ชัน + เวลาล่าสุดที่ยังออนไลน์
> (ใช้แสดงในหน้า Dashboard เท่านั้น ไม่มีเนื้อหากิจกรรมอยู่ในนั้น)

## ไฟล์ Excel

เก็บ **1 ไฟล์ต่อวัน** ที่โฟลเดอร์ `logs/` ข้างตัวโปรแกรม เช่น `logs/activity_2026-10-14.xlsx`
คอลัมน์: `Date | Time | Event | Application | Detail | Path | Duration (s)`

คอลัมน์ **Path** ตอนที่หน้าต่างที่ active คือ **File Explorer** จะได้ path ของโฟลเดอร์ที่เปิดอยู่จริงแบบแม่นยำ
(ผ่าน Shell COM API) ส่วนโปรแกรมอื่นๆ (Word, Excel, Notepad, โปรแกรมดูรูป/PDF ฯลฯ) ตั้งแต่ v0.4.7 เป็นต้นไป
จะพยายามเดา path ของไฟล์ที่เปิดอยู่ให้ด้วย โดยดูจาก **ไฟล์ที่โปรแกรมนั้นเปิด handle ค้างไว้จริง** แล้วเลือกไฟล์ที่
นามสกุลหน้าตาเหมือนเอกสารจริง (เช่น .docx .xlsx .pdf .txt .jpg ฯลฯ) — ไม่ใช่ API ที่รับประกันความถูกต้อง 100%
เพราะ Windows ไม่มี API กลางที่บอกได้ชัดว่า "ไฟล์ไหนเปิดอยู่" สำหรับทุกโปรแกรม บางโปรแกรม (เช่น Notepad ฝั่ง
Windows 11 ที่เป็น Store app) ไม่เก็บ handle ไว้ที่ไฟล์จริงเลย กรณีนี้จะปล่อย Path ว่างไว้เหมือนเดิม (คอลัมน์ Detail
ที่โชว์ชื่อหน้าต่างอยู่แล้วยังเป็นตัวช่วยสำรองที่ดีสำหรับกรณีนี้)

> **ไฟล์ของวันที่เริ่มเขียนก่อนเครื่องจะอัปเดตมาถึง v0.4.0** (ตอนยังไม่มีคอลัมน์ Path) จะถูก**แก้ header ให้ถูกต้องอัตโนมัติ**
> ทันทีที่โปรแกรมเขียนแถวถัดไปหลังอัปเดตแล้ว (ไม่เสียข้อมูลเดิม แค่แทรกคอลัมน์ Path เข้าไปให้ครบ) — ถ้าเปิดไฟล์ค้างไว้ตอนที่
> โปรแกรมกำลังแก้ header ให้ปิดแล้วเปิดใหม่เพื่อดูโครงสร้างล่าสุด

## รันตอนพัฒนา (Python)

```bash
pip install -r requirements.txt
python main.py
```

## Build เป็น .exe (ในเครื่อง)

```bash
build.bat
```
ได้ไฟล์ `dist\MAN_inspection.exe`

## Build + Release อัตโนมัติ (GitHub Actions)

ทุกครั้งที่ push ขึ้น branch `main`:
1. GitHub Actions build ทั้ง `MAN_inspection.exe` และ `MAN_inspection_admin.exe` บน Windows runner
2. สร้าง Release ติด tag `v<version>` (เวอร์ชันอ่านจาก `activity_logger/__init__.py`)
3. แนบทั้งสองไฟล์ไว้ใน Release

**เวลาจะปล่อยเวอร์ชันใหม่**: แก้ `__version__` ใน [activity_logger/\_\_init\_\_.py](activity_logger/__init__.py) ให้สูงขึ้น แล้ว commit + push

## การอัปเดตตัวเองของ .exe

**ทั้งสองโปรแกรมอัปเดตตัวเองได้** (`MAN_inspection.exe` และ `MAN_inspection_admin.exe` แยกจากกัน
แต่เช็ก Release เดียวกัน — ตัวไหนก็ดึงไฟล์ของตัวเองไป):

- **`MAN_inspection.exe`** (พนักงาน): เช็กตอนเปิดโปรแกรม + ทุก 6 ชั่วโมง อัปเดตแบบเงียบๆ ไม่มี popup
- **`MAN_inspection_admin.exe`**: เช็กตอนเปิดโปรแกรม (เงียบๆ ถ้าล่าสุดอยู่แล้ว) + มีปุ่ม
  **"Check for updates"** มุมขวาบนให้กดเช็กเองได้ทันที ถ้าเจอเวอร์ชันใหม่จะโชว์ข้อความที่ status bar
  สักครู่แล้วปิด-เปิดตัวเองใหม่ให้อัตโนมัติ

ถ้าเวอร์ชันบน GitHub ใหม่กว่า จะดาวน์โหลด `.exe` ตัวใหม่มาแทนที่ตัวเองแล้วรีสตาร์ท
(ไม่ต้องฝัง token เพราะ repo เป็น public)

ปรับ owner/repo ได้ที่ [activity_logger/config.py](activity_logger/config.py)

> **ถ้าเครื่องไหน "เปิดไม่ขึ้นเลย"** ทั้งที่ Scheduled Task รันสำเร็จ (0x0): อาการนี้เคยเกิดจาก
> กลไก self-update เองค้าง (แก้แล้วใน v0.3.8) — เช็ก `C:\ProgramData\MAN_inspection\app\` ว่ามีไฟล์
> `MAN_inspection.exe.new` หรือ `%TEMP%\*_update.bat` ค้างอยู่ไหม ใช้ [deploy/diagnose.ps1](deploy/diagnose.ps1)
> วินิจฉัยได้เร็วสุด (`irm .../deploy/diagnose.ps1 | iex`) ถ้าเจอให้รัน [deploy/install.ps1](deploy/install.ps1)
> ซ้ำ (เลี่ยงกลไก self-update ที่ค้าง โหลดผ่าน PowerShell ตรงแทน)

> **ถ้าเจอ error "API rate limit exceeded for \<IP\>"** ตอนรัน `install.ps1` หรือเช็กอัปเดต:
> แก้แล้วใน v0.4.2 — เดิมใช้ `api.github.com` ซึ่งจำกัด **60 ครั้ง/ชม. ต่อ 1 IP** (ทุกเครื่องในออฟฟิศ
> ที่แชร์ IP สาธารณะเดียวกัน ใช้โควต้าร่วมกันหมด เครื่องเยอะ+เช็กถี่ก็หมดโควต้าได้ง่าย) เปลี่ยนมาใช้
> URL แบบ redirect ของ GitHub (`github.com/.../releases/latest/download/<ไฟล์>`) แทน ซึ่งไม่โดน
> limit นี้เลย — อัปเดตเป็น v0.4.2 ขึ้นไปแล้วจะไม่เจอปัญหานี้อีก

## Admin Console — dashboard + ตั้งค่าส่วนกลาง

หน้าตาใช้ธีม modern flat (ttkbootstrap) ปรับขนาดหน้าต่างได้ แท็บ Policy เลื่อน scroll ได้ถ้าเนื้อหายาวกว่าจอ

เปิด `MAN_inspection_admin.exe` จะเจอ 2 แท็บ:

### แท็บ Dashboard

ตารางแสดง**ทุกเครื่องที่เคยรันโปรแกรม**: Hostname, **Assigned to** (ชื่อคนที่ใช้เครื่องนั้น ถ้าตั้งไว้),
Machine ID, เวอร์ชัน, สถานะ (🟢 Online / ⚪ Offline), heartbeat ล่าสุดเมื่อไหร่
รีเฟรชอัตโนมัติทุก 60 วินาที หรือกด **Refresh now** เอง

ถือว่า "Online" ถ้า heartbeat เข้ามาใน 15 นาทีล่าสุด (heartbeat ปกติส่งทุก 5 นาที เผื่อพลาดได้ 2-3 ครั้ง)

#### หน้าต่าง Machine details — ดูสถานะ + log ทั้งหมดของเครื่องนั้น

เลือกเครื่องในตาราง → กด **Machine details…** (หรือ **ดับเบิลคลิก** แถวนั้น) จะเห็น:

- **Assigned to** — ช่องแก้ไขได้ ใส่ชื่อ/แผนกของคนที่ใช้เครื่องนี้ แล้วกด **Save** (หรือกด Enter ในช่อง
  ก็ได้ตั้งแต่ v0.4.9) — เก็บไว้ส่วนกลาง (ไฟล์เดียวกันทุก admin console เห็นตรงกัน) ใช้ตรวจสอบได้ว่า
  เครื่องไหนเป็นของใคร เวลามีกิจกรรมผิดปกติ ตารางบน Dashboard จะอัปเดตชื่อให้ทันทีหลัง Save สำเร็จ
  ไม่ต้องกด Refresh ซ้ำ

> **v0.4.9:** ก่อนหน้านี้กด Save แล้วข้อมูลบันทึกจริง แต่ข้อความยืนยัน ("Saving...", "Saved.") ไปโชว์
> ที่สถานะของหน้าต่างหลัก (Admin Console) ซึ่งมักถูกหน้าต่าง Machine details บังอยู่ — เลยดูเหมือน
> กด Save แล้วไม่มีอะไรเกิดขึ้นเลย ทั้งที่จริงบันทึกสำเร็จ ตอนนี้ข้อความยืนยันโชว์ในหน้าต่าง Machine
> details เองแล้ว เห็นชัดเจนไม่ต้องสลับหน้าต่าง
- **Request status** — สถานะคำขอ "log วันนี้" ล่าสุด:
  - ยังไม่เคยขอ → ปุ่ม **Request log now** กดขอได้เลยจากในนี้
  - ⏳ **Pending** (กำลังรอเครื่องนั้นอัปโหลด) → มีปุ่ม **Cancel request** ถ้าเปลี่ยนใจ/กดผิด
  - ✅ **Ready** (อัปโหลดเสร็จแล้ว พร้อมชื่อไฟล์ + เวลาที่เสร็จ) → กด **Download & open** หรือ **Download…** ได้ทันที หรือ **Request again** เพื่อขอไฟล์ใหม่ล่าสุดอีกรอบ
- **Request a specific file** — พิมพ์ **path เต็มของไฟล์ใดก็ได้** บนเครื่องนั้น (เช่น
  `C:\Users\<name>\Documents\report.xlsx`) แล้วกด **Request file** — ใช้ workflow เดียวกับ Request log
  (Pending → Cancel ได้ / Ready → Download) แต่:
  - จำกัดขนาดไฟล์ **20 MB** (ไฟล์ใหญ่กว่านี้จะขึ้นสถานะ ⚠ Failed พร้อมเหตุผล)
  - ไฟล์ที่ไม่พบ/เข้าถึงไม่ได้ ก็ขึ้น ⚠ Failed เหมือนกัน (ไม่ค้างเป็น Pending ตลอดไป)
  - **พอกด Download แล้ว ไฟล์จะถูกลบออกจาก data repo ทันที** (เปลี่ยนสถานะเป็น 📦 **Collected**) —
    ป้องกัน repo บวมจากการขอไฟล์บ่อยๆ ยังกด **Request again** ขอไฟล์เดิม/ไฟล์อื่นต่อได้ตามปกติ
    (log รายวันไม่ถูกลบแบบนี้ เพราะอยากเก็บไว้ตรวจสอบย้อนหลัง)

> **v0.4.13:** แก้บั๊กจริงจัง — ไฟล์ที่ขอ (โดยเฉพาะไฟล์ใหญ่ๆ เช่น PDF หลายหน้า) ขึ้นสถานะ
> "Collected" เหมือนดาวน์โหลดสำเร็จ แต่พอเปิดไฟล์ที่ได้มากลับเปิดไม่ได้ สาเหตุคือ GitHub API ที่เรา
> ใช้อ่านไฟล์มีข้อจำกัดที่ไม่มีเอกสารชัดเจน: **ไฟล์ที่ใหญ่กว่า 1MB จะได้เนื้อหาว่างเปล่ากลับมาเงียบๆ
> โดยไม่ error ใดๆ** (ฝั่งอัปโหลดไม่มีปัญหานี้ ผ่านไปได้ปกติ จึงดูเหมือนสำเร็จทุกอย่าง) ตอนนี้ถ้าเจอ
> เนื้อหาว่างแบบนี้จะไปดึงผ่าน Git Blobs API แทนโดยอัตโนมัติ (ไม่มีข้อจำกัด 1MB) ทดสอบจริงแล้วกับ
> ไฟล์ขนาด 2.5MB ผ่าน repo จริง เนื้อหาตรงกันทุก byte
- **Last downloaded on this computer** — จำไว้ว่าครั้งล่าสุดคุณดาวน์โหลดไฟล์ไหน (ทั้ง log และไฟล์ที่ request)
  เก็บไว้ที่ path ไหน เมื่อไหร่ (เก็บเฉพาะในเครื่อง admin เครื่องนี้)
- **All uploaded logs** — รายชื่อไฟล์ log ทั้งหมดที่เครื่องนั้นเคยอัปโหลด ดาวน์โหลดย้อนหลังได้ทุกวัน

มีปุ่ม **Refresh** ในตัวหน้าต่างเองด้วย กดดูสถานะล่าสุดได้โดยไม่ต้องปิดแล้วเปิดใหม่ (v0.4.9: ปุ่มนี้
ถูกตรึงไว้ด้านล่างสุดของหน้าต่างเสมอแล้ว ก่อนหน้านี้หน้าต่างมีขนาดคงที่แต่เนื้อหาในหน้าต่างค่อยๆ เพิ่มขึ้น
เรื่อยๆ ตามฟีเจอร์ใหม่ จนเนื้อหายาวเกินกว่าที่หน้าต่างจะแสดงได้หมด ทำให้ปุ่ม Refresh ที่อยู่ล่างสุดโดนบัง/
หลุดจอไปโดยไม่รู้ตัว — ตอนนี้ถ้าเนื้อหายาวเกินจะมี scrollbar ให้เลื่อนดูได้แทน ส่วนปุ่ม Refresh จะมองเห็น
ได้เสมอไม่ว่าจะเลื่อนไปตรงไหน)

> ไฟล์ Excel เป็น **1 ไฟล์ต่อวันต่อเครื่อง** เสมอ (เช่น `activity_2026-10-16.xlsx`) — กด "Request log now"
> กี่ครั้งในวันเดียวกัน ไฟล์ใหม่จะ**ทับของเก่าด้วยเนื้อหาล่าสุดเสมอ** ไม่สร้างไฟล์ซ้ำ

#### ลบเครื่องออกจาก Dashboard (v0.4.14)

เลือกเครื่องในตาราง → กด **Delete machine…** จะต้อง**พิมพ์ชื่อเครื่อง (hostname) ให้ตรงเป๊ะเพื่อยืนยัน**
ก่อนถึงจะลบได้ (ป้องกันกดลบผิดมือ) เมื่อยืนยันแล้วจะลบถาวร: สถานะล่าสุด, Assigned-to, คำขอค้างต่างๆ
(log/file/force-update), และ **log ที่เคยอัปโหลดทั้งหมด** ของเครื่องนั้น — ไม่สามารถกู้คืนได้

> **หมายเหตุสำคัญ:** การลบนี้ลบแค่ข้อมูลในฝั่ง data repo เท่านั้น **ไม่ได้ไปหยุดโปรแกรมบนเครื่องจริง**
> ถ้าเครื่องนั้นยังรันโปรแกรมอยู่ heartbeat รอบถัดไปจะทำให้เครื่องนั้นโผล่กลับมาในตารางอีกครั้งแบบ
> ไม่มีประวัติเก่าเลย (เหมือนเครื่องใหม่) — เหมาะสำหรับล้างเครื่องทดสอบ/เครื่องที่เลิกใช้แล้วและ
> uninstall ไปแล้วจริงๆ ถ้าอยากให้เครื่องหยุดรายงานตัวถาวร ต้อง uninstall โปรแกรมที่เครื่องนั้นด้วย

#### ขอ log เดี๋ยวนี้ (เช่นตอน debug ไม่ต้องรอตามรอบ schedule)

กด **Request log now** (จากตาราง Dashboard หรือในหน้าต่าง Machine details) → เครื่องนั้น (ถ้าออนไลน์อยู่)
จะอัปโหลด log ของ**วันนี้**มาให้ภายใน **~15-20 วินาที** แทนที่จะต้องรอรอบ schedule เป็นวัน/สัปดาห์/เดือน

ทำงานยังไง: เครื่องพนักงานเช็ก "มีคำขอไหม" ทุก 15 วินาที ด้วย conditional request (ETag) ของ GitHub
ซึ่ง**ไม่กินโควต้า rate limit เลยถ้าไม่มีคำขอใหม่** (ทดสอบยืนยันแล้ว) จึง poll ถี่แบบนี้ได้อย่างปลอดภัย
แม้มีพนักงานหลายเครื่องใช้ token เดียวกัน

#### ปิดฟีเจอร์นี้ชั่วคราวได้ (เผื่อกดถี่เกินไปจนมี log เข้ามาเยอะ)

ในแท็บ **Policy** มีสวิตช์ **"Enable on-demand requests"** (หมวด "On-demand requests") — ปิดสวิตช์นี้แล้ว
**Save & Publish** จะทำให้:
- ปุ่ม **Request log now** ใน Admin Console เป็นสีเทา กดไม่ได้ทันที (มี popup เตือนถ้าพยายามกด)
- เครื่องพนักงานทุกเครื่อง**เลิก poll หาคำขอไปเลย** (ไม่เสีย API call แม้แต่น้อย) จนกว่าจะเปิดสวิตช์กลับ

เหมาะกับตอนที่ส่ง request ไปเยอะเกินจำเป็นแล้วอยากหยุดชั่วคราว โดยไม่กระทบ schedule อัตโนมัติอื่น (upload/email ยังทำงานตามปกติ)

> หมายเหตุ: การอัปโหลด/ส่งอีเมลที่เกิดจาก schedule อัตโนมัติหรือจาก "Request log now" ของ admin
> **ไม่มี popup เด้งที่เครื่องพนักงานเลย** (ทำงานเงียบๆ เบื้องหลัง) จะมี popup ให้เห็นแค่ตอนพนักงาน
> **กดเองจาก tray menu** เท่านั้น (เช่น "Upload today's log now") ดูสถานะ/ประวัติที่แท้จริงได้จาก Admin Console Dashboard แทน

### แท็บ Policy — ปรับได้ครบ จากที่เดียว ส่งผลทุกเครื่องพร้อมกัน

| หมวด | ปรับอะไรได้ |
|------|------------|
| **Monitoring** | เปิด/ปิดการเก็บ: หน้าต่างที่ใช้งาน, idle/active, USB, lock/logon แยกแต่ละอย่าง + ปรับ poll interval, idle threshold, heartbeat interval |
| **Central upload** | เปิด/ปิดการอัปโหลด log ไป data repo (รายวัน/สัปดาห์/เดือน + เวลา) — **แนะนำให้เปิดเป็นค่าเริ่มต้น** เพราะไม่ต้องใช้ความลับอะไรเลย + ตั้ง **"Keep uploaded logs for (days)"** ได้ (ค่าเริ่มต้น **10 วัน** — เครื่องพนักงานจะลบ log เก่ากว่านี้ของตัวเองออกจาก data repo อัตโนมัติทุกวัน กันไม่ให้ repo บวมไม่รู้จบ ใส่ `0` เพื่อเก็บไว้ตลอดไปไม่ลบ) |
| **Email** | ส่งต่อเป็นอีเมลด้วย (เสริม ไม่บังคับ) — ผู้รับ + รอบส่ง |

กด **Load current** เพื่อดึงค่าปัจจุบันมาดู, แก้แล้วกด **Save & Publish** → เครื่องพนักงานทุกเครื่องจะดึง
policy ใหม่ไปใช้ภายใน **heartbeat interval ถัดไป** (ปกติไม่เกิน 5-10 นาที เร็วกว่าของเดิมที่ใช้ repo public มาก)

### ตั้งค่าครั้งแรก (ทำครั้งเดียว)

1. สร้าง **GitHub fine-grained token** สำหรับตัวเอง:
   GitHub → Settings → Developer settings → **Fine-grained tokens** → Generate new token
   → **Resource owner**: `T-TFIG` → **Repository access**: Only select repositories → เลือก **`MAN_inspection-data`** (repo private ตัวใหม่ ไม่ใช่ repo โค้ด)
   → Permissions → **Contents: Read and write**
2. เปิด `MAN_inspection_admin.exe` → วาง token ลงช่อง **Access token** (ใช้ปุ่ม **Paste** ไม่ใช่ Ctrl+V ถ้าเครื่อง Windows ตั้ง locale ไม่ใช่อังกฤษ เพื่อกัน token เพี้ยน) → โปรแกรมโหลด dashboard + policy ให้อัตโนมัติ

token นี้เก็บไว้ในเครื่อง admin เท่านั้น (`%ProgramData%\MAN_inspection\admin_settings.json`) ไม่ขึ้น repo

## ส่ง log ไปเครื่อง admin — 2 ช่องทาง (เลือกได้จาก Policy)

### 1) Central upload (แนะนำ, ค่าเริ่มต้นที่ดีกว่า Gmail ตรงๆ)

เครื่องพนักงานอัปโหลดไฟล์ Excel ไปที่ **private data repo** โดยตรง ตามรอบที่ตั้งใน policy (รายวัน/สัปดาห์/เดือน)
ไม่ต้องมี Gmail/App Password อยู่บนเครื่องพนักงานเลยสักตัว — admin ดูได้ทันทีจาก Dashboard → View logs

ทำไมดีกว่า Gmail ส่งตรงจากทุกเครื่อง:
- ไม่มี credential ที่ส่งเมลได้อยู่บนเครื่องพนักงาน (ลดความเสียหายถ้าเครื่องโดนแฮ็ก)
- เห็นสถานะ/ประวัติการส่งจาก Dashboard แทนที่จะต้องไปไล่เปิดอีเมล
- พนักงานกดส่งเองได้ทันทีด้วย: คลิกขวาไอคอน tray → **Upload today's log now**

> ⚠️ **ข้อจำกัดที่ควรรู้**: client token (สำหรับอัปโหลด) ฝังเหมือนกันทุกเครื่องที่ build จาก CI เดียวกัน
> ถ้ามีคนแกะ `.exe` ออกมาเจอ token จะ**อ่าน/เขียนไฟล์ของเครื่องอื่นในที่เก็บกลางได้ด้วย** (ขอบเขตสิทธิ์เป็นระดับ repo ไม่ใช่ระดับไฟล์)
> แต่จำกัดอยู่แค่ repo ข้อมูลส่วนตัวนี้ repo เดียว ไม่กระทบโค้ด/Release สาธารณะ และ**ตั้งค่าได้แค่คนที่มี token นี้เท่านั้น**
> ถ้าสงสัยว่า token รั่ว ให้ revoke token เดิมใน GitHub Settings แล้วสร้างใหม่ใส่เป็น Actions secret แล้ว build ปล่อยเวอร์ชันใหม่

### 2) Email (Gmail) — เสริม ไม่บังคับ, admin ตั้งค่าเอง

ยังใช้ได้เหมือนเดิม ถ้า admin อยากได้สำเนาในอีเมลด้วย ต้องตั้ง secret ที่เครื่องที่จะ "ส่ง" (ปกติแค่เครื่อง admin เครื่องเดียวพอ ไม่ต้องทุกเครื่องพนักงาน):

1. เปิด 2-Step Verification ในบัญชี Gmail ผู้ส่ง แล้วสร้าง **App Password**
   (Google Account → Security → App passwords) — SMTP ใช้รหัสปกติไม่ได้
2. คัดลอก [email_config.example.json](email_config.example.json) เป็น `email_config.json` กรอก `sender_email` + `app_password`
3. วางไฟล์ไว้ที่ `C:\ProgramData\MAN_inspection\email_config.json`

> ⚠️ **ห้าม commit `email_config.json`** (repo public — App Password จะโดนเห็น) — ถูก `.gitignore` ไว้แล้ว

## ตั้งค่า CI ให้ build ที่มี central upload (ทำครั้งเดียว โดยเจ้าของ repo โค้ด)

ตัวไฟล์ `.exe` ของพนักงานต้องมี "client token" ฝังมาตอน build เพื่ออัปโหลด/heartbeat ได้:

1. สร้าง **GitHub fine-grained token อีกตัว** (แยกจาก token ส่วนตัวของ admin):
   Resource owner `T-TFIG` → Repository access: only `MAN_inspection-data` → Permissions: **Contents: Read and write**
2. ไปที่ repo โค้ด `T-TFIG/MAN_inspection` → **Settings → Secrets and variables → Actions → New repository secret**
   ตั้งชื่อ `CLIENT_DATA_TOKEN` ใส่ค่า token จากข้อ 1
3. push โค้ด (หรือกด Run workflow) ตามปกติ — CI จะฝัง token นี้ลงใน `.exe` ของพนักงานให้อัตโนมัติ
   (ถ้าไม่ตั้ง secret นี้ไว้ ตัว `.exe` จะ build ได้ปกติแต่ฟีเจอร์ central upload/dashboard จะปิดเงียบๆ เหมือนตอนยังไม่มี secret)

## ข้อควรรู้ด้านกฎหมาย/ความเป็นส่วนตัว (สำคัญสำหรับ admin)

เครื่องมือนี้เก็บ **ชื่อโปรแกรม + ชื่อหน้าต่าง + path (เท่าที่ดึงได้) + เวลา + เหตุการณ์ (idle/lock/USB)** ของพนักงาน
และส่งให้ admin — ถือเป็นการ **monitoring พนักงาน** ก่อนนำไปใช้จริง admin ควร:

- **แจ้งพนักงานให้ทราบ** และขอความยินยอมตามที่กฎหมายกำหนด (เช่น PDPA ของไทย / GDPR)
- ใช้กับ **เครื่องของบริษัท** และเพื่อวัตถุประสงค์ที่ชอบด้วยกฎหมายเท่านั้น
- ปรึกษาฝ่าย HR/กฎหมายของบริษัทเรื่องนโยบายการเก็บและใช้ข้อมูล

> ⚠️ **"Request a specific file"** ใน Machine Details คือสิทธิ์ที่กว้างกว่าการดู activity log ปกติมาก —
> admin สามารถดึง**ไฟล์ไหนก็ได้** (ถ้ารู้ path) จากเครื่องพนักงานมาดูได้โดยตรง ควรใช้เฉพาะกรณีมีเหตุผลทางธุรกิจ
> ชัดเจน (เช่น ตรวจสอบ/forensics ตามนโยบายบริษัท) และอยู่ในขอบเขตที่แจ้งพนักงานไว้แล้วเท่านั้น

โปรแกรมออกแบบให้ **โปร่งใส**: มีไอคอน tray ให้เห็นว่ากำลังทำงาน และไม่เก็บการพิมพ์คีย์บอร์ดหรือภาพหน้าจอ

### จากเครื่องพนักงานเอง

คลิกขวาไอคอน tray → **Check for updates** จะเด้ง notification บอกทันที:
- `Up to date (v0.3.2).` — ล่าสุดอยู่แล้ว
- `Updating to v0.3.3 — the app will restart shortly.` — เจอเวอร์ชันใหม่ กำลังอัปเดตให้ (จะปิด-เปิดใหม่เอง)

> ปกติ `.exe` เช็กอัปเดตให้เองอยู่แล้วตอนเปิดโปรแกรม + ทุก 6 ชั่วโมง ปุ่มนี้มีไว้เผื่ออยากเช็กทันทีไม่ต้องรอ

### บังคับให้เครื่องพนักงานอัปเดตทันที (จาก Admin Console)

ไม่ต้องรอพนักงานกดเองหรือรอ 6 ชม. — ใน **Machine details** ของเครื่องนั้น มีหมวด **"Force update"**
กด **Force update now** → เครื่องนั้น (ถ้าออนไลน์อยู่) จะเช็กและอัปเดตให้ภายใน **~15-20 วินาที**
เหมือนปุ่ม "Check for updates" ที่พนักงานกดเอง เพียงแต่ admin เป็นคนสั่งจากระยะไกล

ผลลัพธ์โชว์ในหมวดเดียวกัน (กด **Refresh** ในหน้าต่างถ้ายังไม่เห็น):
- `Up to date (v0.4.0).` — ล่าสุดอยู่แล้ว ไม่มีอะไรต้องทำ
- `Updating to v0.4.1 — the app will restart shortly.` — เจอเวอร์ชันใหม่ กำลังอัปเดต เครื่องนั้นจะปิด-เปิดใหม่เอง

> **ถ้าหลัง force update แล้วเครื่องขึ้น cmd วูบๆ ซ้ำๆ แล้วเงียบไปเลย (ขอ log/ไฟล์ไม่ได้อีก):**
> ก่อนหน้านี้ถ้าขั้นตอน swap ไฟล์ล้มเหลว (เช่น antivirus สแกนไฟล์ที่โหลดมาใหม่ค้างไว้) เครื่องจะเปิด
> ตัวเก่ากลับมาแล้ว "เช็กอัปเดตซ้ำทันที" วนไม่จบ — แต่ละรอบเปิด cmd แวบหนึ่งเพื่อลอง swap ใหม่
> และที่สำคัญคือแอปไม่มีทางไปถึงขั้นฟัง request เลยเพราะมันเช็กอัปเดตก่อนเริ่มงานอย่างอื่นเสมอ

#### ขอ log ตามช่วงเวลา (v0.4.22)

ใน **Machine details** มีหมวด **"Request log by time range"** — กรอกวัน (`YYYY-MM-DD`) และเวลา (`HH:MM` แบบ 24 ชม.) ของ
